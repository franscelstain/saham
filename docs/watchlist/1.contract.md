# docs/watchlist/1.contract.md

## Tujuan
Dokumen di folder `docs/watchlist/` adalah acuan utama untuk membangun fitur watchlist. Dokumen ini harus sinkron dengan codebase dan test, supaya tidak ada salah tafsir.

## Definisi

### CONTRACT
CONTRACT = aturan yang **mengikat implementasi** (code + output).  
Jika terjadi konflik antara docs dan code, maka **code dianggap salah** sampai disamakan.

CONTRACT mencakup:
- Struktur output (payload keys, types, required/nullable)
- Algoritma/perhitungan (skor, ranking, guard, threshold)
- Reason codes + semantics
- Urutan proses/pipeline (step-by-step)

### LOCKED
LOCKED = bagian dari CONTRACT yang **tidak boleh diubah diam-diam**.  
Perubahan LOCKED hanya sah bila dilakukan lewat “Change Control” (lihat bagian bawah) dan selalu ikut mengubah:
1) docs, 2) code, 3) tests/fixtures.

LOCKED biasanya meliputi:
- weights skor
- clamp/normalization range
- guard thresholds
- RR/stop constraints
- reason codes enumerations
- field names pada payload

## Source of Truth

### Contract documents
Semua file di `docs/watchlist/` adalah CONTRACT, **kecuali**:
- `docs/watchlist/8.strategi.md` (operasional/pipeline eksekusi, bukan kontrak angka/rumus)
- `docs/watchlist/7.schema.md` (struktur DB, bukan kontrak angka/rumus)

Catatan:
- Walau 8.strategi.md & 7.schema.md bukan kontrak algoritma, tetap harus konsisten dengan implementasi (mis. command yang disebut harus benar).

## Aturan Konflik (Docs vs Code)
Jika ada perbedaan:
1) Default: **code harus mengikuti docs**
2) Jika ternyata docs yang keliru, lakukan perubahan lewat “Change Control” (docs → code → tests), bukan patch code diam-diam.


## Anti-duplikasi (Wajib)
- Dokumen **tidak boleh** menyalin ulang definisi/aturan yang sudah ada di `1.contract.md`.
- Jika butuh menyebut ulang, gunakan **tautan/rujukan** (mis. “lihat 1.contract.md bagian X”).
- Tujuan: tidak ada dua penjelasan berbeda untuk rule yang sama.

Khusus reason codes:
- Reason yang **shared** lintas policy wajib diletakkan di `docs/watchlist/5.reasons_catalog.md` (prefix `GL_*`).
- Policy docs hanya mendefinisikan reason codes spesifik policy (`WS_*`, `DS_*`, `PT_*`, `IL_*`) dan override yang benar-benar berbeda.

## Change Control untuk LOCKED

### Status perubahan
Perubahan LOCKED harus melalui 3 status:
1) **PROPOSAL**: usulan perubahan nilai/rumus, belum mengikat
2) **EVALUATED**: sudah diuji dengan backtest/replay A/B dan metrik tersimpan
3) **PROMOTED**: menjadi LOCKED baru (docs + code + tests sudah update)

### Syarat minimal PROPOSAL
PROPOSAL harus menyebut:
- nilai lama → nilai baru
- alasan (kontradiksi internal, mismatch input/kontrak, atau evidence)
- dampak yang diharapkan (apa yang membaik dan kenapa)

### Wajib A/B untuk perubahan LOCKED
Setiap PROPOSAL LOCKED harus diuji dengan A/B:

- **Baseline**: LOCKED lama
- **Candidate**: LOCKED baru (proposal)

Keduanya dijalankan pada:
- policy yang sama
- range tanggal yang sama
- universe yang sama
- sumber data yang sama

### Wajib snapshot config per run
Setiap run harus menyimpan snapshot parameter yang dipakai:
- policy name
- semua parameter LOCKED (weights/threshold/range)
- identifier versi code (commit hash / build_id / tag)
- tanggal range

### Metrik minimal yang harus dicatat
Minimal per policy per run:
- counts: Top/Secondary/Watch/Avoid/NoTrade
- coverage: % hari ada kandidat (Top+Secondary > 0)
- skor: avg/median/p95 score_total
- reason codes: top N reason paling sering muncul (guards/flags)
- jumlah “hard reject” vs “soft flags” (kalau ada)

Opsional (lebih kuat):
- simulasi hasil trade sederhana (entry/stop/tp) untuk N hari, konsisten dan repeatable

### Kriteria promote
PROPOSAL boleh dipromote jadi LOCKED baru jika:
- metrik tidak memburuk secara material, dan
- ada improvement yang jelas sesuai tujuan policy (coverage, kualitas, guard noise turun, dsb), atau
- perubahan memperbaiki kontradiksi/mismatch yang fatal.

## Aturan Implementasi Kode

### Per-policy vs umum
- Logic yang **berbeda per policy** harus hidup di `app/Trade/Watchlist/Policies/*Policy.php`
- Logic yang **umum** (shared) harus hidup di komponen shared (Evaluator/Validator/Builders), bukan copy-paste di policy atau engine
- `WatchlistEngine` hanya orchestrator, bukan tempat rule policy

### Single Source of Truth untuk CONFIRM
CONFIRM/intraday eligibility harus melalui evaluator strict (satu jalur), bukan duplikasi logic.

## Test Gates (wajib ada)
Project harus punya test yang mengunci CONTRACT:
1) **Contract output tests**
   - required keys, types, nullable/required, no extra keys
2) **Policy score tests / golden master**
   - fixture input kecil per policy, snapshot score_components + score_total + group
3) **Doc-config alignment tests**
   - weights/threshold di code sama dengan LOCKED di docs

## Prinsip
- Boleh berkembang, tapi tidak boleh berubah diam-diam.
- Setiap perubahan LOCKED harus traceable, repeatable, dan terkunci lagi lewat tests.

## Data Degradation Rules (Missing/Unreliable Data)

Prinsip: aplikasi pribadi + data provider bisa bolong. **Missing data bukan sinyal negatif.** Watchlist harus tetap jalan, dan alasan harus transparan lewat `reasons[]`.

### Defaulting

- **Ticker status**: bila data status manual untuk `ticker_id + trade_date` tidak ada, maka status dianggap **`REGULAR`**.
  - Defaulting ini **harus transparan** lewat `reasons[]` dengan reason object: `{code:"GL_TICKER_STATUS_DEFAULTED_REGULAR", severity_level:"WARN"}`.
  - Hanya status yang eksplisit (mis. `SUSPENDED`, `DELISTED`) yang boleh jadi **HARD_EXCLUDE**.
- **Corporate action hint (`ca_hint`)**: bila `ca_hint` kosong/null, artinya **tidak ada informasi** (bukan berarti aman). Tidak boleh jadi hard reject.

### Candidate Reasons (LOCKED)

Candidate reasons adalah alasan per-ticker yang menjelaskan kenapa kandidat lolos/di-block/di-exclude.
Agar **tetap per-policy** dan anti ambigu, **severity tidak di-encode di dalam `code`**.

**Reason object (candidate)**
- `code` (string, REQUIRED)
  - **Policy-scoped**: `WS_*`, `DS_*`, `PT_*`, `IL_*` (contoh: `WS_MIN_DV20_IDR`, `DS_EVENT_MISSING`)
  - **Global/shared**: `GL_*` (contoh: `GL_TICKER_STATUS_DEFAULTED_REGULAR`, `GL_CA_SPLIT_WINDOW`)
- `severity_level` (enum, REQUIRED)
  - `INFO` (tag/informasi, tidak memblokir)
  - `WARN` (peringatan, tidak memblokir)
  - `SOFT_BLOCK` (memblokir **entry eligibility**, tapi ticker **tetap tampil** minimal `watch_only`)
  - `HARD_EXCLUDE` (ticker dikeluarkan dari payload kandidat)

Catatan:
- `message` boleh ada untuk human-readability, tapi **tidak boleh jadi source of truth** untuk logic.
- Mapping utama ke behavior harus ditentukan oleh `severity_level` (LOCKED).

#### Outcome class (LOCKED)
Untuk menghindari duplikasi aturan antar policy docs, istilah outcome di docs mengikuti kelas ini:

- **EXCLUDE** ⇒ `severity_level=HARD_EXCLUDE` (ticker dikeluarkan dari payload kandidat)
- **NOT_QUALIFIED** ⇒ `severity_level=SOFT_BLOCK` (entry tidak eligible, tapi ticker tetap tampil minimal `watch_only`)
- **WARN** ⇒ `severity_level=WARN` (peringatan, tidak memblokir)
- **INFO/TAG** ⇒ `severity_level=INFO` (tag/informasi, tidak memblokir)

Catatan:
- Policy docs **tidak boleh** mendefinisikan ulang mapping istilah di atas. Jika perlu, cukup rujuk ke bagian ini.

### Meta Reasons vs Candidate Reasons (LOCKED)

Ada **2 schema alasan** yang berbeda dan **tidak boleh dicampur**.  
Keduanya sama-sama disebut “reason”, tapi beda tujuan.

#### A) GlobalReason (run-health / allocation-health) — pakai `severity` (LOCKED)

Dipakai untuk hal yang **tidak spesifik 1 ticker**, misalnya readiness data, hasil allocator, atau keputusan global.

- **Schema (LOCKED)**:
  - `code` (string, required)
  - `severity` (`INFO|WARN|ERROR`, required)
  - `message` (string, optional)
  - `meta` (object, optional)

- **Paths yang memakai GlobalReason (LOCKED)**:
  - `meta.*.reasons[]`
  - `recommendations.reasons[]`
  - `recommendations.skipped[].reason`
  - (jika ada modul lain yang memberi alasan global, wajib ikut schema ini)

- **Dampak**:
  - Tidak langsung mengubah `score_total` kandidat.
  - Bisa mengubah `meta.flags[]` / menandai bahwa hasil perlu di-hold atau allocator tidak bisa berjalan optimal.

#### B) CandidateReason (per ticker / explainability) — pakai `severity_level` (LOCKED)

Dipakai untuk alasan **per ticker**, baik di group watchlist maupun di rekomendasi/tranche.

- **Schema (LOCKED)**:
  - `code` (string, required; boleh `GL_*` atau `WS_*`/`DS_*`/`PT_*`/`IL_*`)
  - `severity_level` (`INFO|WARN|SOFT_BLOCK|HARD_EXCLUDE`, required)
  - `message` (string, optional)
  - `meta` (object, optional)

- **Paths yang memakai CandidateReason (LOCKED)**:
  - `groups.*[].items[].reasons[]`
  - `recommendations.items[].reasons[]`
  - `recommendations.items[].execution_slices[].reason`

- **Dampak (mapping outcome class)**:
  - `severity_level=HARD_EXCLUDE` ⇒ kandidat **tidak muncul** di groups.
  - `severity_level=SOFT_BLOCK` ⇒ entry **tidak eligible**, tapi ticker tetap tampil minimal `watch_only`.
  - `severity_level=WARN|INFO` ⇒ tidak memblokir entry.

Catatan:
- Policy docs **tidak boleh** mendefinisikan ulang schema/mapping di atas. Jika perlu, cukup rujuk ke bagian ini.
